# 方法-AI产品对标追赶的评测驱动

**一句话结论**：AI 产品效果不如标杆时，先把差距归因到 Harness/Eval 而非模型；用"对标 baseline 的评测基准"驱动 generation-verification loop 去追，不要凭感觉改——没有可量化基准，就会原地打转、永远追不上。

## 背景 / 问题
团队在建某 AI 产品的新版本（如竞Mate 之于竞品数据平台），对标一个已有标杆（如 workbuddy），但"效果还不如标杆"。直觉反应往往是"换更强的模型"或"整体感觉不行、再改改"——两者都容易空转。

## 结论 / 做法
1. **先归因，不先换模型**：按 [[参考-2027AI发展趋势预判]] 的判断，模型层正被快速拉平，差异化在 Harness（上下文工程、工具调用健壮性、长程任务可靠性）与 Eval。落后标杆的根因大概率在这里，而非模型。
2. **建"自己 vs 标杆"的评测基准**：把标杆当 baseline，拆成几十条可打分的真实任务。每次迭代都能回答一句话——"这版追上了几分？"。这是把"追上 workbuddy"变成**可验证目标**（呼应 Robin Looping：设可验证目标 / 找可验证可打磨的问题，用解 coding 的方式解）。
3. **trace 归因到环节**：用全链路 trace 把失败 case 一条条拎出来，定位是上下文没给够、工具调用失败、还是能力本身弱——而不是整体感觉"不行"。
4. **generation-verification 周迭代**：先生成改进、再跑分验证、看曲线补短板。coding 进步快的根因就是每步可验证；AI 产品一旦有了可验证基准，就能用同样方式快速逼近并反超。

## 反例 / 边界（何时不适用）
- **遗留系统别硬 AI 化**：若标杆要替代的是一个老旧、数据库不具备 AI 改造现实性的系统，正道不是"把老系统评测驱动地改造成 AI"，而是老系统 **keep-alive 封顶守成**、用新品追赶达标后迁移用户、再 sunset；切忌新旧双投。（见 [[jingmate]] L1）
- **撤人力的时机**：新品评测分未追平标杆前，不要提前撤掉老系统的维护人力（尤其面向大用户量时），先稳后迁。
- 若差距经 trace 确属模型硬能力缺口（可验证域都压不住），才回到换/调模型——这是少数情况，不是第一反应。
