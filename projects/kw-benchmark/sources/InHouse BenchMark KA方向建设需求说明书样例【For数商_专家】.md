1. 目标招募专家画像
行业与职业分布：﻿http://10.21.223.137:8860/industry_occupation_matrix.html﻿
本方向招募能够将真实业务工作拆解为可验证、多文件、多交付物任务的行业专家。
专家不要求具备 Agent 或编程背景，但必须熟悉对应业务流程、常用资料和实际交付标准，能够判断一份交付物是否真正可用、是否存在关键遗漏或逻辑错误。
优先招募有5年以上相关工作经验、熟悉真实业务文件和日常工作流程的专家。专家必须能够提供经过脱敏或虚构改造的真实工作场景，并说明在实际工作中如何判断交付结果是否合格。
题目中不得出现真实客户名称、真实个人敏感信息、身份证号、手机号、银行账号或公司未公开数据。可以使用虚构公司、虚构客户和脱敏数据，但任务逻辑、文件关系、业务约束和判定标准应尽量保留真实工作的特征。
2. 任务说明
Knowledge Artifact（KA）是以一个或多个具体文件作为主要交付结果的任务。
专家需要把自己日常工作中真实存在、频繁发生、机械耗时但不能出错的完整工作任务/工作环节，改造成可交给AI完成的多文件任务，并同时提供任务所需的参考资料、标准答案、非满分交付物和可逐条核验的评分判据。
一道题应尽量同时具备以下三个要素：
1.
多源：需要阅读、比对或整合多个原始材料文件；
2.
有矛盾或逻辑难点：不同文件之间存在口径差异、遗漏、冲突、版本切换或需要反向核算的地方；
3.
多交付物：要求产出多个相互关联的文件，其结论、数据和建议应保持一致。
不建议提交以下题目：
•
需要访问真实内网系统、数据库、账号或权限的任务；
•
含真实客户、真实个人信息或未公开企业数据的任务；
•
答案随时间变化，或没有唯一正确答案及可判定范围的任务；
•
只考写作风格、创意、美观度的任务；
•
不需要阅读参考文件、凭常识即可完成的任务；
•
一个简单动作即可完成的任务，例如单纯排序一张表；
•
必须依赖付费墙或无法提供给答题者的资料才能完成的任务。
3. 参考的对标基准
本方向参考以文件交付和真实工作任务为核心的公开基准测试设计思路，重点吸收以下类型基准的特点：
•
GDPval 类任务：强调真实职业场景、专业人员参与出题以及最终文件交付物
•
JobBench 类任务：强调任务文件夹、任务指令、评分 Rubrics、任务说明书和标准答案之间的完整配套
5. 难度设计
请为每道题标注 1–5 分难度，并在任务说明中简要解释难度来源。也可以在内部说明中补充基础、中等、困难三档描述。

难度不能只靠增加文件数量堆高。高难度应来自真实的业务判断、跨文件关联、数据矛盾、版本口径、异常定位或多交付物之间的一致性要求。每个陷阱都必须可从提供的文件中查证，不能依赖专家未写明的行业常识。
建议同时记录以下信息：
•
Difficulty：1–5 分；
•
Representativeness：职业代表性，1–5 分；
•
Estimated time to complete：专家预计完成时间，按小时记录。
6. 提交格式
一道题对应一个独立文件夹，命名为 ﻿task1﻿、﻿task2﻿ 等。文件夹应包含以下内容：
﻿
Plain Text
复制内容
task1/
├── task_folder/                         # AI 完成任务所需的原始资料
│   ├── TASK_INSTRUCTIONS.txt            # 任务指令，放在 task_folder 内
│   ├── source_file_1.xlsx
│   ├── source_file_2.pdf
│   ├── source_file_3.docx
│   └── source_file_4.csv
├── RUBRICS.json                         # 评分 Rubrics
├── task_card.md                         # 内部任务说明书
└── answer_folder/                       # 标准答案 / 参考答案
    ├── deliverable_1.xlsx
    ├── deliverable_2.docx
    └── verification_log.csv
﻿
6.1 ﻿task_folder﻿
•
放置 ﻿TASK_INSTRUCTIONS.txt﻿ 以及题目需要用到的全部附件；
•
附件数量不少于 3 个，尽量混合至少 3 种不同格式；
•
单个文本文件不超过 20 万字符；
•
公司名、人名和客户名全部虚构，个人敏感信息不得进入题目；
•
可以混入少量容易与目标文件混淆的材料，但每个陷阱必须可解；
•
文件内容必须处处自洽，除刻意设计的矛盾外，不得出现编号、日期、合计或明细之间的无意错误；
•
如果使用外部资料，应在 ﻿task_card.md﻿ 中记录文件用途和完整来源 URL。
6.2 ﻿TASK_INSTRUCTIONS.txt﻿
文件应使用清晰、口语化的任务指令，至少包括：
1.
AI 需要扮演的角色和业务场景；
2.
需要完成的具体动作；
3.
各数据源的优先级、裁决规则和适用版本；
4.
主数据范围、阈值、生效日期、四舍五入规则等约束；
5.
需要单独标记、上报或降级处理的异常情况；
6.
交付物清单、文件名、格式和内容要求；
7.
﻿﻿task_folder/﻿ 中所有参考文件的完整文件名列表。
﻿﻿TASK_INSTRUCTIONS.txt﻿ 应明确告诉 AI 要做什么，但不能直接泄露参考答案或评分判据中才应发现的关键结论。指令中不得要求交付 Rubrics 中没有对应要求的额外文件，也不能使用“合理即可”“自行判断”等无法核验的表述。每道题的指令长度不少于 450 个中文字或 300 个英文词。
6.3 ﻿RUBRICS.json﻿
•
根节点使用 ﻿rubrics﻿ 数组；
•
每道题包含 10–20 个 Rubric，先尽量完整编写，后续审核时可删除无效或低效项；
•
每个 Rubric 包含 ﻿rubric﻿、﻿weight﻿ 和 ﻿criterion﻿ 字段；
•
﻿﻿weight﻿ 只能使用 6、8、10；
•
每个 Rubric 包含 3–6 条 criterion；
•
只有一个 Rubric 下的所有 criterion 全部通过时，才能获得该 Rubric 的权重；任意一条未通过，该 Rubric 记 0 分；
•
题目得分 = 已通过 Rubric 权重之和 ÷ 全部 Rubric 权重之和；
•
每条 criterion 必须写清楚正确答案、应出现在哪个交付物中，以及必要的数值、对象、文件名或判断结论；
•
如果交付物包含图片，且图片内容需要进入评分，criterion 中必须包含 ﻿plot﻿、﻿figure﻿、﻿visualization﻿、﻿visualize﻿、﻿heatmap﻿、﻿histogram﻿、﻿scatter plot﻿、﻿biplot﻿、﻿diagram﻿ 或 ﻿q-q﻿ 等英文关键词，否则判分系统可能不会把图片发送给判分模型，最多支持 8 张图片；
•
除刻意设计的矛盾外，附件中的合计、明细、编号和日期必须相互吻合；
